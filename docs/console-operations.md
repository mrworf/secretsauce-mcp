# Instance console operations

The console runs behind an operator-managed HTTPS reverse proxy. Route `/console` and `/console/*` to the gateway; preserve the trusted request Origin. Do not derive the console origin from Host or forwarded headers. Set `CONSOLE_STORAGE_DIR` to a persistent, protected writable directory and `CONSOLE_KEY_FILE` to a stable separately mounted mode0600 encryption-key file. One application process owns this store. Keys and storage must survive restarts; losing the key prevents decryption. Keep the independent backup recovery material separately. [Encrypted instance backups](console-backups.md) support manual/download and reviewed daily mounted-directory scheduling; copy ciphertext off-host. Restore installation and reenrollment remain M17.

Stop the application for the deliberate host setup command. In a protected interactive terminal, with `CONFIG_PATH`, `CONSOLE_STORAGE_DIR` and `CONSOLE_KEY_FILE` set, run `node dist/consoleSetup.js https://console.example.org`. For initial unclaimed setup it durably creates a protected key if absent; after a managed marker exists, missing key material fails closed. It snapshots the explicit gateway baseline and displays a single-use30-minute proof only in that terminal. Do not redirect the command to general logs. Restart normally and open `https://console.example.org/console`. Paste the proof, enroll the Owner password and authenticator, and save the once-displayed recovery codes and independent backup material. Neither visiting the URL nor a GET consumes a proof or creates authority. Reissue by stopping the process and rerunning the host command. Reissue cancels incomplete enrollment.

The browser stores no secret in persistent application storage. QR/manual enrollment is local, noncacheable and without third-party resources. Reverse proxies must suppress authentication request bodies, cookies and Authorization values from logging. No secret belongs in a console URL. The CLI proof and enrollment values are operator-controlled capabilities, not general diagnostics.

Encrypted snapshots use AES256GCM with fresh nonces; passwords use salted scrypt; recovery material and browser session identifiers are hashed. Writes fsync a protected temporary file, atomically rename and fsync the directory. A protected managed marker prevents silent YAML fallback. Failed or incomplete writes never imply successful setup. Audit uses authenticated chained records with durable starts before effects and durable completion after state commit; incomplete starts remain uncertain. Host administrators can alter files and control keys, so the journal is tamper-evident rather than tamper-proof. Keep storage/key permissions and disk capacity healthy.

All console users require password and authenticator-app TOTP. Passwords contain15–1024 Unicode characters and are checked against a bounded vendored10k common-password corpus; this does not recognize every breached password. Password managers/paste are supported; there are no composition or periodic-expiry requirements. Successful TOTP counters are persisted and cannot be reused, including concurrent submissions. After enrollment, wait for a fresh code to sign in. Per-account five failed attempts cause a60-second lockout; source/global admission caps limit abuse before unbounded audit storage growth.

Sessions use hashed random identifiers and Secure/HttpOnly/SameSite=Strict host cookies, expire after30minutes idle or12hours total, and are limited to10per identity/500total. My account lists only your sessions; revoking another session rejects other identities. Password replacement requires your current password plus a fresh TOTP and revokes all your sessions. The action-bound recent verification primitive lasts5minutes and does not authorize an unrelated operation. Factor replacement/recovery and user management are delivered in milestone12. Administrative roles do not grant MCP execution.

Durable audit admission is mandatory in managed and explicit YAML modes. Configure `audit.file`, or mount writable `AUDIT_STORAGE_DIR` (default `data`, with `gateway.jsonl`). Mount the entire audit directory: its JSONL, `.chain`, `.chain.head`, `.key`, `.managed` and `.writer` ownership material form one journal. No temporary-storage fallback exists. One process owns the directory; runtimes in that process share one chain writer. Missing keys/checkpoints, changes to recorded events, complete-line suffix truncation, competing writers and uncertain process ownership fail closed. The local checkpoint detects edits to history when the protected checkpoint/key remain trusted; a host administrator controlling both remains outside that guarantee.

Public `/health` returns only `ready` or `not_ready`. Audit outage blocks sensitive console, OAuth and gateway reference/dispatch effects before credential substitution or downstream calls. Existing reliable identities retain their own scoped reads. New password/TOTP login during an audit outage is restricted diagnosis only, and is denied if identity storage, throttle or replay persistence is unreliable. Repair on the host; do not disable audit in the web interface. Stop the instance, restore trustworthy journal/key material and writable storage, then restart. Restart verifies the protected checkpoint and durably records recovery; the recovery record explicitly states that an outage interval or lost evidence may be unknown. A restricted session never upgrades after repair: sign out and authenticate normally with a fresh code.

If an effect occurred but completion could not be recorded, the UI returns an operation ID and a status check instead of success. After repair, the affected identity can inspect that operation; possession of an ID alone grants no access. Password changes may have invalidated the old session, so authenticate again before checking. Initial setup has no ordinary actor yet: stop the instance and use `node dist/consoleSetup.js --status <operation-id>` in the protected host terminal, with the existing key/storage settings. Check initialized state as well as operation status. Do not blindly replay an uncertain effect. An admitted start without a completion remains uncertain across restart; no automatic downstream retry occurs.

Managed instances temporarily refuse the legacy built-in password-only OAuth authorization flow, all built-in token exchanges/refreshes, and previously issued built-in access tokens for MCP POSTs. Enrolled multi-user MFA consent is delivered in milestone14. Public OAuth metadata remains available. Explicit unmanaged YAML deployments preserve their existing built-in OAuth flow under mandatory durable audit; configured external OAuth and bearer gateway compatibility also remain. Neither bearer nor external OAuth creates console authority. Once a managed marker exists, CLI startup reads the encrypted committed configuration directly, with no dependency on or fallback to obsolete YAML.

Browser evidence can be reproduced with `npm ci`, `npx playwright install chromium`, then `npm run test:console:browser`. Set `PLAYWRIGHT_BROWSERS_PATH` to a writable persistent or temporary directory when needed. The harness uses real local HTTPS and the installed declared Chromium, resolves the synthetic `console.example.org` name to loopback, advances only its server clock between TOTP uses, and records no network bodies/traces/videos. Enrollment screenshots mask all synthetic seed/QR/recovery/input values. The in-app Browser was unavailable in this session; the declared standalone harness supplies rendered evidence.

### Assisted password reset

People & Access exposes **Reset password** for eligible other people. Owners may target other roles; Administrators may target Administrator, Auditor and Member accounts. Invitations, role changes and disable/reactivation remain Owner-only. Verify the person independently through an established channel, select its category, then confirm your password and a fresh authenticator code. Do not choose a replacement contact.

Issuing the 30-minute link does not interrupt existing access. The recipient supplies a new password and their existing authenticator code or one unused recovery code. Completion retains MFA, revokes prior sessions and client access, and requires ordinary sign-in. A link alone cannot reset a password. Old incompatible reset links require authorized reissue.

### Assisted Authenticator reset and uncertain outcomes

Use **Reset authenticator** separately from password reset. Confirm the named target and existing trusted-channel verification, then reauthenticate. This immediately invalidates the old authenticator, recovery codes, sessions, client grants and temporary references. The recipient enrolls a fresh authenticator and saves new recovery codes without entering or replacing their password. Normal sign-in follows. If both password and factor were lost, finish Authenticator enrollment first, then issue a new password reset.

Expired, cancelled or undelivered Authenticator links leave the person restricted. People & Access shows the notification outcome and permits eligible initiators to cancel or reissue; failed SMTP never rolls recovery back. A second active enrolled Owner must remain. Use the existing host-local recovery route if continuity prevents an assisted reset.

New reset authority upgrades the encrypted local state format to version 2; old binaries reject it rather than reinterpret reset proofs. Do not downgrade state or restore old factors to retry an uncertain operation. Restart reads durable reset intents: if identity persistence failed before publishing the security transition, the affected identity is restricted with old factors and sessions cleared. Inspect the recorded operation, repair host storage, then use authorized fresh Authenticator recovery (or protected host recovery for a final Owner). A transition already published retains its newer generation and is never reversed. Backup archives continue their existing portable schema; restore retains the local compatibility version.
