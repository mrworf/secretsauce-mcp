# UX12 bounded domain basis

Proposed specialist resolution for reconciliation, not canonical authority or runtime acceptance. Roles applied separately: Product UX (shared task and presentation rules), software architecture (identity/routing and transaction boundaries), security (authorization, revocation and recovery boundaries). Inputs are confirmed PO-FB290–298 and inherited UX11/STATE/SECRES contracts. No new owner decision is needed for the following bounded derivations.

## U12-01 — Aligned lifecycle rows

Use shared column tracks for corresponding name/status/draft/action content across Active, Inactive and Archived rows. A longer archived action must not shift its badge or preceding columns independently. Preserve existing responsive stacking, full action labels, keyboard reachability and status meaning. This applies to the whole Services list, not a special archived-row offset. Existing desktop appearance and narrow reflow remain the approved family.

## U12-02 — Review entry refreshes safely

Overview and editor/footer review actions enter the same ordinary review task. Missing credential values are ordinary precise Authentication blockers: show the actual incomplete settings review without approval authority, not a stale-comparison detour. Preserve local unsaved guided/Advanced content, selected tab/history, pending removal intents and independent current access.

A stale shared base may be refreshed automatically only after a fresh authorized read proves the same managed identity/incarnation and unchanged proposal baseline: same saved-draft existence, generation and exact proposal content/removal intents, or the same applied baseline for an unsaved proposal. Independently changed credential availability and current grants are freshly inspected, not required to equal the old inspection; they may produce ordinary blockers and never permit reuse of old approval. Numeric generation equality alone is insufficient after Apply, discard or recreation. Reconcile current independent assignments rather than replaying a draft grant snapshot. If these checks hold and eligibility is unchanged, retain the user's local edits, advance only the safe dependency baseline and attempt the normal save/inspect/review sequence at most once. Do not use the existing blind manual generation reload as an automatic implementation.

Changed/deleted/discarded/applied/recreated proposals, genuinely competing edits, revoked permissions, unknown write outcomes and generic network failures are not eligible. Retain work and show the established actionable conflict/unknown-outcome recovery. Never retry approval/Apply automatically or mint approval for incomplete settings. This is a narrowly proven rebase, not last-writer-wins or repeated background retries.

## U12-03 — A real public MCP service reference

The editable value is the actual key MCP clients supply for service discovery, policy descriptions and requests, not a display alias. Preserve the stable managed identity and service incarnation beneath it; independent credentials, assignments, audit/history and management routes remain attached to that identity. Explain in Details: this reference identifies the service in MCP requests; manual creation accepts the user-chosen reference; import starts from the YAML service key and allocates a collision-safe target when occupied. Display name remains separately editable. Copy copies the currently displayed reference with clear proposed/current distinction when a draft differs.

Inactive editable services expose the field normally. Active services show a read-only field with adjacent Change reference action. Its accessible warning dialog explains that changing the reference can break existing client requests and invalidates previously issued service/credential/response references. Confirm unlocks editing only; it neither renames nor applies anything. Cancel leaves it locked and unchanged. Archived and role-read-only views retain their existing edit restrictions. Guided and Advanced editing must not bypass the same reference validation, warning acknowledgment and review consequences.

Stage the proposed reference with the ordinary draft; Save changes never changes current routing. Review shows exact before/after reference and disruption; Apply publishes it atomically. Discard/cancel preserves the current reference. An already-published Inactive service remains Inactive when applying a reference-only change; do not accidentally activate it because the current generic Apply implementation sets Active. Never-published first Apply keeps existing activation behavior. Preserve existing semantics for other changes; this clause does not authorize a general lifecycle redesign.

## D12-01 — Namespace and transaction binding

Separate internal identity from public routing throughout runtime publication and authorization. References are exact and case-sensitive; no silent case folding, trimming, truncation or automatic old-key alias. Preserve unchanged legacy valid imported keys; deliberate new/edited references use the established bounded new-reference syntax and reject invalid/duplicate input precisely. Use own-property-safe lookup and enforce uniqueness across retained current service references (including Inactive/Archived) and accepted saved proposals. Unsaved local typing does not reserve a key. Revalidate namespace availability at save, review and Apply; concurrent claims cannot overwrite another service. A canceled/discarded proposal releases only its pending claim; successful rename releases its old public name without retaining an alias. Reuse is permitted only through deliberate fresh selection of a released reference (including an explicitly supplied YAML service key), never as identity/authority reuse. Automatic collision suffix allocation skips retired references known in retained bounded history; this does not introduce permanent reservation or an unbounded tombstone ledger. Revocation and incarnation fences remain unconditional after history retention expires.

Bind review and confirmation to stable identity/incarnation, old/proposed key, exact draft generation/content, current namespace/dependency revision, lifecycle, actor/session and existing security exceptions. Publish routing removal/new binding plus the reviewed configuration in one durable transaction. An Inactive rename must not create an executable runtime entry. Preserve current assignments and exact values, existing credential-cleanup intents and independent mutation timing. Audit records identify the stable target and old/new public keys without secret values.

## D12-02 — Revocation, uncertain outcomes and retained evidence

Before admitting downstream work, resolve the public key to the current stable identity/incarnation and check current authorization, lifecycle, destination and policy. Existing user OAuth authority is not broadened by renaming: a public name is not an access grant. Invalidate configured credential/service tokens and response-secret references associated with the affected binding; fence both old and new public-key generations. Requests queued before publication must recheck binding before substitution/dispatch. Already-dispatched work may complete with its captured response protection but cannot mint usable references after revocation. Reusing an old key for another service cannot revive old tokens, queued work, grants or response references.

Unknown persistence is reconciled as one old/new rename transaction using incarnation-bound evidence, never an independently replayed dictionary rename. Fence affected live authority after admitted uncertain publication and require durable reread before success/retry. Delete/archive, history-as-draft and stale editor actions use stable identity/incarnation and may not resurrect an old routing binding or operate on a replacement. Historical audit labels remain historical; historical configuration reused as a draft must pass current namespace validation and reviewed Apply.

Introduce the necessary monotonic reader-format boundary before admitting persistent separated routing semantics; old readers must fail closed, and every writer/restore path must preserve a newer format. Existing records migrate deterministically with public reference equal to their existing key, retaining identity, values and assignments without silent activation. Portable encrypted recovery preserves the explicit reference/identity relationship while assigning fresh local incarnations and retaining existing recovered-Inactive/review gates. Exclude local pending rename/replay authority at owned schema paths. Sanitized YAML exports use the applied public key and remain importable; import still creates independent managed identities and collision-safe public references, never reuses target credentials/grants. Pending reference edits must not masquerade as current export state.

## Evidence and required validation

Source inspection: consoleServicePage Details presently presents editor.id as immutable; review entry saves before inspection. consoleServices uses the managed dictionary key throughout assignments, review, config publication and deletion and Apply unconditionally selects Active. registry.getService/listVisibleServices expose/look up service.id; tokens.TokenRecord and ResponseSecretTokenRecord bind public service strings, while revoke/responseContext maintain per-service generation fences. Therefore reference editing is a product/state/security change, not a text-field-only fix. Independent lifecycle-row action tracks explain the reported alignment risk; source inspection alone is not runtime visual certification.

Canonical adoption needs PRD configuration/reference/review criteria, UX Details/review/list patterns, STATE identity/namespace/transaction/recovery clauses and SECRES binding/revocation/old-reader clauses, with corresponding coverage/journeys. Delivery must prove positive and negative new reference syntax/collision/concurrency cases; retained legacy literals; inactive rename versus first activation; same identity/values/current grants after Apply; old-key rejection and safe reuse; queued and in-flight fences; uncertain-write/restart and prior-reader rejection; delete/history/import/export/restore; safe single refresh versus changed/discarded/recreated/unknown proposals; incomplete credential review from both entry points; actual desktop/narrow/enlarged lifecycle alignment and warning/modal/history/Advanced behavior. This document makes no claim that these new behaviors are implemented or tested.
