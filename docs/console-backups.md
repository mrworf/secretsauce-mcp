# Encrypted instance backups

Owners open Settings → Backups & restore and confirm their password and a fresh authenticator code before downloading a backup or changing independent material. Manual creation requires current Owner authorization and explicit confirmation. Keep the independent recovery material received at setup separately from this host and from authenticator recovery codes. Earlier instances can enable encryption by supplying their original saved setup material with recent authentication; this does not replace that material.

Format 1 uses a versioned recovery-key derivation, an ephemeral X25519 key exchange, HKDF-SHA256 and AES-256-GCM. The instance keeps only a public wrapping key and a verifier. The archive and independently held material alone decrypt the included state on a clean host; no original application encryption key is required. Included audit integrity keys travel only inside encrypted ciphertext. Anyone holding both archive and material can read included credentials: protect both.

Archives include services/destinations/policies/scanners/revisions, managed downstream credentials and encrypted system secrets, users/roles/assignments/password verifiers, settings and retained integrity-verified audit. They exclude sessions, OAuth grants/refresh tokens/codes, MFA seeds/recovery codes, invitations/recovery links, gateway references, downstream data, images and proxy configuration. Legacy bearer access material is excluded and needs later explicit reactivation. A recovery point identifies the coherent included revision and both audit heads; recovery-point time and manifest assembly time are distinct from the actual completed job time, recorded after verified disk publication. An archive cannot establish later host publication or off-host copying by itself.

Only one backup or restore job may run. Capture pauses process writes briefly with a five-second bound; encryption/publication follows with a 30-second job deadline, 192 MiB archive ceiling, 512 MiB directory ceiling and at most 64 directory files. Across configured directories, the retained archive/unknown-outcome catalog is also capped at 64 entries and 512 MiB; changing directories cannot bypass that bound. The catalog keeps all retained completed archives plus up to 36 recent other jobs, within 100 entries; failures cannot erase the last valid archive metadata. The UI reports stages rather than invented percentages. A running job becomes unknown after restart. Failed or uncertain output cannot be downloaded or replace a previously verified completed archive. Repair audit/key/storage/mount capacity on the host before deliberately retrying; never steal application/audit leases.

Manual backups initially use a protected application-local backup subdirectory unless a separate mounted directory is configured. Copy ciphertext off-host. Local storage does not protect against host loss. Restore installation and reenrollment are a separate milestone; the bounded decryption/validation interface does not extract arbitrary filesystem paths or activate archived access.

Owners save daily schedule, mounted directory, UTC hour and retention as a draft, then review exact deletion impact and apply with recent authentication. Daily scheduling attempts once per due UTC day; failures or interrupted attempts are recorded without pretending that the conditional 24-hour RPO was met. Default retention is 30 days, and the latest accessible integrity-verified archive is retained even if expired. Storage capacity never silently shortens retention. A deletion failure is separate from known successful archive publication. Keep the backup directory separate from live app/audit mounts; no symbolic links or arbitrary archive extraction are accepted.

To replace independent material, an Owner recently authenticates, generates it once, saves it separately, and acknowledges that retained archives still need previous material. The instance stores only a purpose-bound, expiring generation verifier until confirmation; chosen, stale, replayed or different material cannot confirm that generation. Material identifiers in archive history show which independently kept material is required. Changing material affects future archives only. Optional SMTP alerts go to an active enrolled Owner through the existing bounded delivery provider; alert failure cannot undo a known completed archive or enable unaudited work.

Unknown jobs reserve bounded catalog capacity until explicitly resolved. After inspecting the host, remove only that job's final `.ssbackup` and `.ssbackup.pending` output if present. The Owner can then acknowledge its unknown outcome; the app checks that both outputs are absent, records the acknowledgement and releases the reservation. History remains unknown and no success/download is inferred. Never remove lease files or unrelated archives.
