# UX9 service semantics — bounded specialist resolution

Scope: confirmed PO-FEEDBACK-2026-11-18-002, PO-FB-238–264; baseline8181af4. This resolves product semantics for reconciliation adoption, not implementation or a complete definition pass. Existing role/audit, immediate credential/access, atomic apply, recovery and exact-literal contracts remain.

## S9-01 — Discard has a named scope

Owner/Administrator editors can discard unsaved browser edits back to the saved draft, or to the applied configuration when no saved draft exists. If this is a never-saved new setup, explicit abandon returns to Services without creating a service. Discarding a saved draft is a separate explicit confirmation naming the service and explaining that saved proposed settings are removed. If unsaved edits also exist, confirmation must name that those are abandoned too; cancelling retains both.

For a saved never-activated service, removing its saved configuration does **not** imply deleting or archiving the service: retain its stable identity/display identity, independent credential values/metadata, historical evidence and applicable current lifecycle. It remains Inactive, has no Draft indicator and no executable configuration; Overview explains setup is needed and exposes ordinary configuration editing. A subsequent edit starts a fresh proposal, not resurrection of the discarded content. This preservation-oriented derivation avoids inventing permanent removal or making Discard undo immediate values. The independently confirmed existing Delete/archive action remains available. An applied service retains its applied configuration and current assignments/lifecycle; Active keeps running it. Archived stays Archived.

Saved discard requires current write authorization, current target/revision/draft generation and durable audit; stale or uncertain outcomes require reload, not a false success. Clear saved review tokens with the discarded proposal. No secret value, immediate grant/revocation, disable/archive outcome or completed credential mutation is undone. Browser-only discard does not pretend to be a durable mutation. A shared persistent service bar uses status, Discard, Save for later, Review changes; direct section navigation replaces Continue and the extra Back to Services controls. Navigation guard Save must finish saving successfully before navigating; failure preserves work and explains it locally.

## S9-02 — Lifecycle presentation is orthogonal

Presentation maps internal Draft/Disabled or any never-activated record to **Inactive**, Active to **Active**, and Archived to **Archived**. **Draft** is a separate saved-proposal indicator only when a saved draft exists. Unsaved changes are editor state, not a saved Draft badge. No storage enum migration is implied. Retain existing disable/archive immediate revocation, unarchive-to-disabled behavior and explicit reviewed activation; restoring archives still requires existing recovery review. Active does not claim reachable/healthy execution: missing applied values can block execution while lifecycle remains Active; missing proposed values do not stop a valid applied configuration.

List rows retain Needs configuration when known required configuration is incomplete. Within service screens, section issues and parent Configuration issue marker replace that duplicate badge. Review changes can open incomplete proposals and list exact issues with section/field fix links; activation remains unavailable until required configuration is valid. Empty access is valid and is never a missing-required-field error. Review does not claim an approval token exists until its server-side activation preconditions pass.

## S9-03 — Imports create independent unassigned services

Every imported service is a new managed service, never an update to a pre-existing active, inactive, archived or draft record. Allocate a unique stable local service ID, using the validated source ID when unused if desired; collisions require a fresh ID. Internal references and deliberately supplied import credential values attach to the allocated target, not the similarly named existing service. Preserve credential identifiers, policies, destinations and supported literals; source service IDs may remain provenance, not authority. Preview/result identifies source-to-created target correspondence without requiring the user to edit internal IDs.

Display name uses source name when free. On collision use `Imported <source name>`, then `Imported <source name> (2)`, `(3)` and the first free successive suffix. Check all retained service records and the whole batch; reserve names/IDs atomically and revalidate at commit to reject stale allocation rather than overwrite. Bounded supported-name/ID limits still apply; impossible bounded allocation returns an actionable error without partial import. Existing same-name services and their values, grants, pending work and lifecycle remain unchanged. Repeated deliberate imports create another separate service; a lost import response must reconcile operation outcome before retry rather than promise idempotent duplicate creation.

Discard source access subjects as executable input; no separate identity mapping is required or offered. New imported proposals start with an empty user/client selection, current assignments empty, and cannot execute before ordinary review/apply. Owners/Administrators can use normal Access & policy eligibility controls to make new explicit selections. Applying with none selected succeeds when other required settings are valid; no identity, including administrators, gains execution access from role or name/email similarity. First activation may atomically apply explicitly reviewed new selections under existing current eligibility checks. Later access remains the separate current immediate action.

## S9-04 — Retire old mapping safely

Existing unresolved imported drafts must become editable/saveable/reviewable without reimport or an identity-mapping screen. Remove missing-mapping blockers and legacy imported identity targets as grant sources. For a never-activated imported draft, clear access entries derived from import/mapping; where provenance cannot distinguish those from later pending selections, reset that proposed selection to empty and visibly state that imported access was reset and can be selected here. This affects a proposal only, not a live grant. Preserve ordinary explicitly selected pending assignments only when their post-import origin is provable, and still require current review/eligibility. Do not infer intent from equal email/name or matching IDs.

For a service with applied configuration/current grants, preserve those current assignments exactly; retiring draft mapping cannot clear, add or replay them. Its imported proposed content must use current authoritative access and the usual later-access action remains independent. Historical imports that previously overwrote a draft retain their current service identity; do not retroactively clone, rename, activate or rewrite past applied history. New imports follow S9-03. Preserve unrelated safe draft fields and immediate credential values; retire mapping metadata and invalidate stale reviews atomically with a new dependency/generation boundary under audited current mutation or controlled upgrade. Mere viewing must not silently mutate access. Uncertain migration/save must fail closed for activation and preserve durable-state recovery. Backup/recovery invariants remain; restored legacy mapping is never live access or an excuse to bypass current restore review.

## S9-05 — Acceptance and downstream boundaries

- Never-saved abandon creates no record; saved never-active discard retains Inactive identity/values and removes Draft; applied discard preserves live settings/grants; Archived discard never restores execution. Cancel/stale/unauthorized and unknown persistence have distinct safe outcomes.
- Review incomplete shows actionable issues and disabled approval; correcting values enables normal reviewed approval; zero assignments passes configuration validation but execution remains denied.
- Import collides against active/inactive/archived/draft and same-batch names; each new target is separate with deterministic name sequence, independent values, empty access and no source-identity grant. Concurrent stale import never overwrites.
- Legacy unresolved draft becomes usable without reimport; pending access reset is visible when provenance is ambiguous, while live grants and unrelated fields/values are preserved. Old reviews cannot apply pre-retirement mappings. Test restore/upgrade only where changed schema/readers require it.
- Current security and architecture review must validate exact migration transaction/revision strategy, compatibility for retired mapping API inputs (reject attempts to grant through them), concurrency and audit uncertainty. Mechanisms remain architecture-owned; these observable outcomes are settled.

Implementation-ready: yes for this bounded semantic contract, subject to canonical reconciliation and targeted downstream definition review. No open material owner decision. No authority to broaden archived deletion, credential cleanup, storage redesign, restore behavior or implementation scope.
