# People and account recovery

The self-hosted instance has four fixed roles. Owners invite predetermined roles, change roles, disable accounts, verify recovery and register exact external issuer/subject pairs. Administrators assign existing eligible identities to services; neither role nor registration automatically grants execution. Auditors inspect non-secret configuration/activity and cannot mutate or execute. Members see assigned services and their own account/activity/clients. All console sign-ins require enrolled password plus fresh TOTP.

Invitations expire in 72 hours. Opening a link performs no activation or consumption. Deliberate enrollment sets a password, displays fresh authenticator material and recovery codes once, and confirms a fresh code before any ordinary access. Reissue invalidates prior proof; revoke leaves pending accounts restricted. Keep a second enrolled Owner when practical: the last active enrolled Owner cannot be disabled or demoted. Changes and session/client revocation take effect immediately.

Password reset preserves MFA. Public reset requests always return the same safe instructions; without configured SMTP an Owner must verify the person through an existing trusted channel and issue a manual link after action-bound recent password/TOTP. Owner assistance records only the channel category (in person, known phone, established contact), immediately revokes sessions/client grants and restricts the account until the selected reset or fresh enrollment completes. An Owner cannot assist their own account: use password plus an existing fresh factor or unused recovery code, or ask another Owner/host operator. Assistance becomes invalid if its issuing Owner loses authority before completion. Recovery expires after 30 minutes; links and codes cannot be reused.

A signed-in user can replace MFA only with password plus current TOTP or an unused recovery code. A locked-out user can use password plus a recovery code through the restricted factor-recovery form. Neither a session nor password alone can replace MFA. Fresh enrollment replaces old codes. Password change/reset and factor recovery revoke prior sessions and client grants.

For all-Owner lockout, stop the single writable instance and repair unavailable audit storage first. Mount the entire stable audit directory with encryption keys/chain/head checkpoints. In a protected host terminal with existing CONSOLE_STORAGE_DIR, CONSOLE_KEY_FILE and audit configuration, run `node dist/consoleSetup.js --recover-owner` to list the bounded non-secret existing Owner identities, then `node dist/consoleSetup.js --recover-owner <existing-owner-id>` for the selected ID. Selection is available only in this protected terminal after audit repair; no public discovery or encrypted-state inspection is needed. The terminal must be interactive; the command cannot be invoked through any web route and cannot read arbitrary requested host paths. It uses existing protected storage/key, records the host recovery, and prints one private 30-minute restricted reenrollment link. Lost/expired material can be reissued with the same command, invalidating prior proof. Restart the service and deliberately complete fresh password/TOTP enrollment before ordinary management access. Never redirect this terminal output into container/general logs. Missing managed key material must be restored, never regenerated.

Links use the trusted configured origin, e.g. `https://console.example.org/console`, with proof in a fragment that does not reach HTTP logs. The browser removes that fragment immediately and keeps it only in transient memory. No-referrer/no-store headers and same-origin POST exchange protect the enrollment step. Do not copy links into diagnostics or audit notes. Reverse proxies must avoid request-body logging and never log recovery fragments or credentials. Durable audit outage blocks issuance, completion and every identity mutation; repair on the host and sign in normally again. Unknown completion must be reconciled using its operation ID before retrying.

SMTP uses optional implicit TLS (normally port 465) with certificate verification, a five-second absolute operation deadline, a 16 KiB reply/body bound and at most four concurrent sends. Save the Owner-scoped draft, review its safe metadata and confirm recent password/TOTP to apply; credentials never reappear. Blank credential preserves current material; explicit Delete removes it on apply. Disable email delivery in the draft/review/apply flow to return to manual links and remove applied SMTP material. Test only a recipient you are authorized to contact. Delivery status is queued, delivered, failed, manual or capacity; SMTP acceptance is delivery status, never enrollment proof. Failure cannot undo recovery or prevent a permitted gateway call. Invitations, resets and account-security notices use the same boundary; later backup/audit notices can call it without adding another sender.

Account and registered external identities have a current non-secret `authorizationGeneration` (legacy absent means zero). Password change/reset, recovery authorization/completion, role/disable changes and session/client revocation increment it in the same encrypted identity transaction. The live broker revokes subject references even if completion recording is uncertain. Multi-user client grants introduced later must capture and recheck this generation against the current eligible identity before access/refresh issuance and every MCP admission; disabling then reenabling never revives an old reference or grant. This field does not activate built-in/external OAuth modes or replace service assignment checks.
