# Shared interaction patterns

## UX-IN01 — Forms and progressive disclosure

Use visible field labels, concise purpose/help text and explicit units. Group related settings into named sections; optional advanced details retain a visible effective summary. Keep one primary next action for the task. Editable forms support keyboard/paste/password managers; credentials are not repopulated after save. Existing credential cards show metadata and **Replace value…**, never a reveal action. Explicit **No downstream authentication** avoids treating an empty credential as an accidental omission.

Save for later (the existing save-draft operation) preserves non-secret input and returns Saved for later · Not in use yet; it does not say Applied. Warn before discarding unsaved work or navigating away; offer Stay, Save for later where allowed, or Discard. Never persist entered secrets in browser storage or reproduce them in recovery notices. Distinguish saved drafts from browser-unsaved edits. A validation failure preserves permitted non-secret input, places the error beside the field, and provides an error summary with focusable links. A secret needing re-entry is labeled explicitly. Global/backend failures use a task-level notice and retry path.

## UX-IN02 — Draft review and concurrency

**Review & apply** opens a full page with the exact reviewed service/settings scope, base revision, sanitized before/after groups, effective policy changes, security exceptions, affected services and expected reconnection/reference effects. Returning to edit preserves the draft. Do not silently include unrelated settings. A stale base/dependency or role change rejects apply with no partial-success claim: explain what changed, show the sanitized comparison, and offer reload/review of the new state while retaining authorized non-secret draft work.

For service review, use separate **Changes** and **New settings** tabs with section-grouped content. Changes compares current applied values with the reviewed proposal; New settings presents the complete sanitized proposal without requiring ordinary users to read a raw object dump. Preserve supported values and exact matching/order semantics; absence of a current applied configuration is explicit. Use labeled addition/removal/change states with restrained green/red/yellow accents when feasible under UX-V02 and UX-A rules. UX-DESIGN-005 approves aligned Before/After columns on wide screens and each paired comparison stacked on narrow screens; UX-IN17 and UX-R07 define the complete realization.

A service review’s **Approve changes** action opens a focused confirmation dialog with **Continue** and **Cancel**, explaining “This will apply changes and make this the active configuration.” If exceptions exist, explain “Before changes can be applied, please review and acknowledge the following,” list each meaningful exception and its affected scope, and require every individual checkbox before enabling Continue. Opening, cancelling or switching review tabs does not apply. Continue submits the exact current reviewed scope; existing stale/dependency, pending and unknown-outcome safeguards remain in force. Exception descriptions use recognizable service/destination context and distinguish inherited TLS defaults from destination overrides; internal identifiers alone are insufficient. This is service review scope, not a redesign of full Settings review or SMTP acknowledgment.

Security-exception acknowledgements identify the specific exception and effect; never bury them in a generic checkbox. Use the policy tester where uncertainty is about matching, without suggesting the test proves credential safety. Apply success names the new active revision and links to activity. Apply failure states that the prior active revision remains, only when that outcome is known. Unknown completion uses status lookup/reconciliation guidance rather than an unsafe repeated operation or false rollback claim.

## UX-IN03 — Immediate and consequential actions

Identity, role and service grants/removals, disable/archive, grant/session revocation and service credential value actions and SMTP credential deletion use a concise explicit confirmation with target, consequence and action verb. Label that they take effect immediately on success and do not wait for draft application. Destructive controls are visually subordinate to routine edit/save until invoked; the confirmation then makes the consequential action unambiguous. Cancel leaves the target unchanged. Do not require typed phrases for every action or introduce approval chains.

Request recent authentication only for the high-risk actions specified by IDENT-06/security contracts. Reauthentication states the bound action and requests required password/TOTP, preserves allowed non-secret task context, and returns to its review after success. Expiry, denial or cancellation does not perform the action. Do not offer password-only MFA replacement or MFA-disable convenience.

The last active Owner protection is explained beside the unavailable operation; name the need for another enrolled Owner. Removing access or disabling a service states that newly admitted requests stop, while already-dispatched work may complete. Archive returns to Disabled when restored. Re-enable explicitly reviews the current service/dependencies. Credential replacement states affected references will be invalidated; service credential Delete explains clear-versus-key-removal under UX-IN14; SMTP retains UX-IN09. Dependency labels and recovery links never expose secret values. History cannot undo these operations.

## UX-IN04 — Policy and effective state

Display actual evaluation order: highest priority first, deny before allow at a tied priority, stable same-effect ties; unmatched requests use the default. No decorative dragging silently changes order. Exact/prefix/regex labels stay explicit. Effective TLS/scanning inheritance and any override are readable before editing.

Safe policy preview takes identity, service, destination, method and path/URL, then shows assignment eligibility, canonical target, winning rule/default, effective secret detection and denial/allow reason. Prominently state **No downstream request is sent**. Invalid input shows field errors; blocked identity or destination shows a negative result with a permissible reason. Never substitute/display credentials or a secret-bearing outbound URL. Preview is informative, not a saved grant or proof that later dispatch will still be allowed.

## UX-IN05 — Feedback and operation states

| State | Observable response and recovery |
| --- | --- |
| Empty | Explain the scope; offer the actor's valid next action (add/import, clear filters, or contact an existing administrator) |
| Loading | Retain page context, label the region busy, and prevent duplicate task submission; avoid endless unlabeled spinners |
| Saved / applied / completed | Use exact status, target and revision/job identity where relevant; do not conflate saved draft, email delivery or enrollment with completed activation |
| Validation failure | Inline error plus linked summary; preserve non-secret work; reveal a collapsed invalid section |
| Forbidden / role changed | Remove stale mutation capability and show safe return; do not leak unavailable object data |
| Offline / request lost | State that the result may be unknown; reload operation state before allowing retry of a consequential action; never queue secret mutations offline |
| Degraded dependency | Describe impacted capability and corrective step; SMTP failure does not claim invitation acceptance or stop otherwise permitted gateway work |
| Partial workflow progress | Separate completed actions from remaining steps (for example restore installed versus users/services reviewed); never call atomic apply partially applied |
| Limit reached | Show relevant non-secret limit/unit and recovery condition; do not silently evict active state or suggest raising a limit without permission |
| Session expired | Explain sign-in is required, preserve only safe non-secret context and return after authentication; all changes still need current checks |

Status notices use words and icon/shape in addition to color. Success may use a transient notification only when persistent page state also confirms it. Failures requiring action remain visible. Long jobs show stage, start time and known progress; never fabricate a percentage when the work cannot be measured. Auto-refresh must not steal focus or repeatedly announce unchanged state.

## UX-IN06 — Enrollment, accounts and connection

Initial setup first proves host authorization, then collects instance/Owner details, password, authenticator enrollment and independently stored backup recovery material. Invitations show predetermined identity/role and expiry. Display fresh authenticator QR plus accessible manual seed only inside the authorized enrollment step; allow code paste, explain clock mismatch without exposing seed in errors, and confirm a valid code before ordinary access. Show recovery codes once with a deliberate save acknowledgement; never later reveal stored codes. Fresh factor enrollment invalidates prior recovery authority according to the security flow.

Login uses password then TOTP with recovery-code access clearly discoverable. Password reset and MFA recovery are distinct: resetting a password does not remove MFA. Expired/used links offer authorized reissue/contact guidance and never expose secret proof. A link preview/GET performs no enrollment. Assisted resets show identity-verification and operation-specific consequence acknowledgement and a safe manual delivery path when SMTP is absent. Manual capability links are visible only in the authorized issuance step, with copy action and expiry; never include them in general history or diagnostics.

Own sessions/client grants show recognisable client/time information permitted by the product, current-session marking and revoke controls. Own password/MFA changes follow the normative checks and announce resulting session invalidation. Read-only diagnostic sessions and restricted recovery use the exceptions in UX-EX01/02.

## UX-IN07 — Backup and restore

Backups show encrypted status, recovery-point and completion times, scope, format/software compatibility, size, job status and retention. Distinguish an in-progress/failed output from a valid archive. Daily scheduling and 30-day default retention are editable Owner settings. State that off-host copying is the operator's responsibility; do not imply a local mount protects against host loss. Download requires recent authentication. Changing retention displays deletion impact before review/apply.

Restore is a full-page sequence: select/upload archive and recovery material → validate → review source/recovery point, contents, current-state replacement, compatibility/capacity, actual initiator and nominated archived Owner → recently authenticate where required → explicitly start restore. Validation failure prevents replacement and gives a safe correct/retry path. Never display recovery material in preview. Clean-host host proof and in-place current-Owner proof remain distinct.

During restore show maintenance and progress stages; stop presenting ordinary write controls. Explain draining work and uncertain downstream outcomes without promising remote rollback. Show pre-restore backup/installation readiness before replacement; failed installation reports whether the prior installation was recovered, fresh login is required, or host recovery is needed. Do not offer arbitrary cancellation after installation begins.

After installation the restricted continuation permits only status and fresh nominated-Owner password/MFA enrollment. Lost/expired continuation gives the protected host-recovery path. After enrollment and healthy audit, show the approved management-review checklist: review people and authorize fresh enrollment; review each disabled service/credentials/policy/access; reactivate external/legacy modes explicitly if wanted; reconnect clients. No **Resume everything** action. Preserve progress across navigation, indicate pending counts, and distinguish this usable management state from an executing service. Re-enabling one reviewed service need not wait for every other service to be reviewed.

Audit history after restore preserves origin/provenance and unavailable intervals. Audit failure at any restore/enrollment stage invokes the outage boundary and blocks ordinary activation.


## UX-IN08 — Separate assisted password and Authenticator resets

From an eligible person detail, present **Reset password** and **Reset Authenticator** as distinct actions. The confirmation names target, operation, established contact and effect; ask the initiator to confirm independent verification and its channel category, not to upload identity documents or enter conversation content. Require current active/enrolled issuer and password/TOTP reauthentication within five minutes. Never let the initiator select a new contact, set the target password or see the target's fresh factor material. Enforce the SECRES-05 role/target matrix server-side as well as in the affordances. The separate reset ceremonies do not change; additional account-edit powers are governed separately by SECRES-06.

Password reset confirmation explains: issuing the 30-minute link leaves current access and MFA intact; completion requires the proof, a new valid password and the target's retained TOTP or unused recovery code. Completion changes the password, consumes the proof/used code, revokes prior sessions/MCP grants/references and requires ordinary login. Existing TOTP and remaining codes are retained. Distinguish issued, delivery failed and completed; issuance must never appear as a changed password or restricted account.

Authenticator reset confirmation explains the immediate consequence: invalidate old factor and recovery codes, revoke sessions/MCP grants/references and restrict the target until fresh factor enrollment. The 30-minute proof permits only confirming fresh TOTP and recovery codes; it changes no password and grants no ordinary access. This verified ceremony does not require the lost factor or forgotten password. Show QR and accessible manual seed only to the target inside restricted enrollment; show new codes once with save acknowledgement. Completion returns an otherwise eligible account to enrollment and requires ordinary password/MFA login. If both credentials are lost, guide MFA recovery first, then issue a fresh password-reset link.

Protect the final active enrolled Owner atomically. Explain why a factor reset is unavailable when no other enrolled Owner can administer; link to the existing protected host recovery guidance. Do not count invited, recovering, disabled or diagnostic-only accounts as continuity. Password-only reset preserves enrolled MFA and does not remove Owner eligibility.

An expired, cancelled or abandoned MFA flow remains restricted; offer currently authorized reissue/host guidance, never restore old factors. Delivery uses SMTP or the existing trusted manual channel; delivery failure does not undo restriction or grant access. Capture/remove capability fragments on load and hash changes; show purpose, expiry and safe status without echoing proofs in errors/history. Expired/replayed proofs, issuer revocation/demotion/recovery, changed issuer/target generations or target promotion beyond issuer authority fail with safe reissue guidance. Natural issuer browser expiry alone does not invalidate the proof or require the issuer to keep a browser open. Audit unavailability blocks issuance/completion; uncertain results require state lookup before reissue/retry. Preserve only authorized non-secret context and never auto-login after either reset.

## UX-IN09 — Independent SMTP credential deletion

In Email, keep SMTP value creation/replacement as write-only input in the ordinary settings draft/review/apply. Provide **Delete SMTP credential** separately from Save/Review/Apply; no delete-on-apply checkbox. Only Owner can invoke it, with recent authentication and explicit confirmation naming the current credential/version and consequences. Administrator reset powers do not permit SMTP management.

If enabled SMTP depends on the value, explain the dependency and link to disabling Email through review/apply first. Disabling retains non-secret settings and saved credential; do not silently delete it or enable anonymous delivery. Once the dependency is absent, deletion removes the live and pending copies, retains non-secret settings, advances version/revision and invalidates old reviews. Show current absence and require refreshed draft review; any later creation/replacement needs freshly entered value in a current draft. Explicit unauthenticated SMTP remains available only as a valid deliberate configuration. State that history does not restore the value and deletion cannot recall already-sent mail or retroactively destroy exported backups.

Stale version/revision, changed permissions, concurrent replacement, dependency or audit failure rejects deletion without deleting a newer value. Missing credential reports already absent, not a new deletion. Preserve safe edits for reload, never rebase a pending secret across deletion. Persistence uncertainty is visibly unresolved and fences use until durable state is known; do not report success or offer blind retry. Queued mail must not use the deleted version; already-dispatched mail can finish under its admitted revision, with no credential resurrection. Retain manual invitation/reset delivery under existing authorization.

## UX-IN10 — Populated forms and setting activation

Ordinary authorized Settings entry is a populated form. With no pending changes label **In use**; saved changes reopen as **Saved for later · Not in use yet**; new browser edits become **Unsaved changes**. For changed values, show the current in-use value locally and in review without a duplicate complete read-only form. Loading cannot masquerade as an empty successful response. Saved credentials are never repopulated.

**Review changes** validates and durably saves currently authorized pending work, then opens review of the complete Settings scope. **Save for later** is the existing save-only alternative and confirms “Saved. Not in use yet. Review and apply to update the running instance.” This is not autosave. Unchanged forms disable no-op submission. Review lists every changed section and exact sanitized before/after effects; **Apply N changes** commits the exact reviewed set atomically. Preserve authorization, concurrency, stale-review, audit and secret-version fencing. Returning to edit retains safe values and selection.

Navigation with browser-unsaved edits offers Stay, Save for later and continue, or Discard unsaved edits and continue. Explicit saved-change discard names scope and requires confirmation; it cannot silently delete another section. Only confirmed durable save yields saved status; failure retains safe local work, and unknown completion requires state lookup. After apply, refresh actual current values, show **Changes applied / In use** and revision, and link to activity. Backup schedule/retention and diagnostic level follow exactly this model. Separately report retention cleanup pending/failure after successful activation. Never label a save as active or falsely claim rollback.

Diagnostics offers **Standard (info)** and **Detailed (debug)** for existing values. Form/current-state labels use the same loaded revision. Live health shows its last-checked time and refresh independently. Read-only actors see current labeled values, without editable controls or forbidden actions.

## UX-IN11 — Required fields, help and repeatable controls

Every mandatory field has a visible asterisk, an adjacent “* Required” legend and programmatic required semantics. Use the red accent consistently without relying on color alone. Conditional required status follows the actual chosen mode. Keep visible labels and short associated help beneath non-obvious inputs, explaining purpose, units, format or effect; placeholders cannot substitute for labels or current values. Error summaries link to fields and reveal invalid disclosures; retain permitted non-secret input.

Repeatable service destinations, credentials and policy rows remain in normal flow. Adding/removing items, errors, expanded help and long text cannot overlap labels, adjacent items or actions. Wizard step numbers and labels must remain visually distinct at every supported width and enlarged text size. Preserve the five-step flow and all existing fields/options. Use paired short fields where useful; URLs and patterns may span the available form width.

## UX-IN12 — Account properties and metadata

**Review account changes** leads to concise confirmation and required recent password/TOTP authentication, then immediate mutation outside configuration drafts. Show the target, changed contact/role and sign-out/revocation effects before confirmation. Contact changes require confirmation of verification through an established trusted channel; record channel category only. Do not change password, MFA, identity, enrollment, lifecycle or restore eligibility. Explain self-contact change ends the current session and requires normal login with the new contact.

Owner can edit permitted users including Owners subject to continuity; Administrator can edit non-Owner targets and choose only Administrator/Auditor/Member, with no self-role change or Owner promotion. Enforce current actor/target/revision at commit, protect final enrolled Owner, and preserve SECRES-06 revocation/proof and uncertainty behavior. Pending/disabled account edits do not activate or rebind old invitation/recovery proofs. Old/new-contact notification failure is a separate delivery result, never a rollback or permission grant. No contact values or credentials in ordinary logs.

Read-only **Created** is durable identity creation. **Last console sign-in** is successful full console admission including the second factor; MCP/OAuth traffic, reauthentication, restricted login and enrollment/reset completion do not count. Never means a tracked account has not signed in; Unknown means no recorded legacy date; external mappings show Not applicable. Restored metadata visibly carries snapshot provenance.

## UX-IN13 — SMTP mode and write-only password

Populate current non-secret SMTP fields directly. A blank replacement-password control says **Password saved. Leave blank to keep it.** or **No password saved**. Preserve explicit authentication choice, deliberate replacement and independent deletion under UX-IN09; mode/port changes never delete credentials or switch authentication silently. Disabled SMTP retains settings/password and cannot deliver.

Encryption offers **TLS (encrypted)** and **None (unencrypted)** only. TLS is the default for new/legacy missing-mode settings; do not infer mode from port, add STARTTLS, or fall back after TLS failure. None shows immediate plain-language warning that messages, invitation/recovery links and any SMTP credentials can be read or altered on the network; recommend TLS or a trusted protected connection. It remains supported with or without deliberate SMTP authentication.

Normal review includes the SECRES-07 explicit acknowledgment and recent authentication when enabling/changing unencrypted endpoint/mode/authentication settings. No extra wizard or repeated dialog for unchanged acknowledged settings. Restored None needs current Owner review/acknowledgment before dispatch. Test clearly uses currently applied settings; pending values must be applied first. An unencrypted test has equivalent visible mode and acknowledgment. Report sanitized failures without secret-bearing protocol data.


## UX-IN14 — Credential dialogs, clearing and attribution

Show each credential’s availability, version and last successful Set/Replace/Clear actor and server time alongside its placement. Display Unknown when trustworthy legacy attribution is absent; renamed/removed actors retain a safe stable attribution and restored metadata is visibly historical/source-qualified. Do not infer the actor from the viewer, email or restoring Owner. Rejected, uncertain and already-empty no-op actions never fabricate a successful last changer.

Use Set value when absent and Replace value when available. Open a focused, named write-only dialog with Save and Cancel. Do not leave an inline required secret input in the ordinary Configuration or wizard page. The dialog explains that saving is immediate and separate from draft placement changes; unrelated Continue neither requires nor submits a secret. Never fetch existing values; clear temporary entry on cancel/completion and keep it out of browser storage, URLs, logs and error echoes. Validation permits re-entry without reflecting the submitted secret.

Delete resolves its current dependencies before confirmation. For an in-use key, say that Delete clears only its value and retains its key; label the final confirmation **Clear value**. Count applied and saved proposed references under STATE-09, including retained Disabled/Archived configuration. If an applied configuration needs the value, explain that new service execution and usable credential-reference issuance are blocked until a deliberate Set supplies it and all other eligibility checks pass. Preserve lifecycle and assignments: show Active with Value missing where applicable, never imply clear has disabled or archived the service. A draft-only dependency blocks that draft’s activation without interrupting unrelated valid applied execution. Clearing an already-empty referenced key states already cleared without a new mutation claim.

An unreferenced key can be deleted; confirmation names key removal. Concurrent replacement, dependency or permission changes require fresh confirmation; never silently switch Clear into Delete or vice versa. Show definite success only after durable outcome; unknown completion requires durable status lookup before retry. Cancel changes nothing. Safe non-secret edits remain for fresh review after invalidation. Discard/history cannot restore the value; earlier encrypted archives may still contain it and only the existing explicit whole-instance restore can recover archived state. Do not promise retroactive backup or forensic erasure. SMTP deletion remains governed separately by UX-IN09.

## UX-IN15 — Service guidance, navigation and repeatable fields

Creation step headers are real navigable links. Direct jumps, section navigation and browser Back/Forward preserve safe non-secret inputs, selected location and return context; they neither silently save nor discard. Final review identifies incomplete sections and links to correction. Explicit save can retain an incomplete draft under existing rules. A tester visit or unchanged navigation alone does not mark the form dirty. Actual unsaved changes get the existing Stay/Save for later/Discard guard; success/unknown save outcomes retain their truthful meanings.

Explain the API documentation URL as a link an LLM can use to understand the service. Allowed destinations describe which servers/base paths may receive requests and credentials. Exact, suffix and regex host matching receive mode-specific explanation/examples without altering literal values. Keep service-default certificate verification visible, explicitly scoped to all destinations without overrides; describe verification of identity rather than confusing disabled verification with disabled HTTPS. Focused advanced destination settings show inherit/on/off overrides and all existing scheme/port/reference options, with a clear return preserving work.

Use contextual placement labels such as Header name or Query parameter name. Explain prefix/suffix as text before/after the credential and show a placeholder-only example, never a resolved secret. Single placement-hint fields stay visible when applicable, with clear grouping and existing generic placement capability preserved. Explain whether header ownership rejects or replaces caller input according to the actual supported semantics. Adding a destination or credential scrolls/focuses its new item and announces it without rerendering to the page top.

## UX-IN16 — Focused rule editing and testing

Render distinct rule rows with readable description, effect, priority, methods and path/host criteria. Highlight rows with any explicit rule-specific secret-detection or binary-scanning override, including a binary override whose configured value equals the current default. Use a readable non-color label distinct from a reduced-protection warning; absence of an override has no override indicator. Keep actual risk acknowledgments governed by POLICY-04. Put Add rule above the list; use concise contextual Edit/Delete labels with accessible item names. No permanently blank add form precedes existing rules. Add and Edit open the same focused dialog and preserve exact imported literals, identifiers, patterns, scanner exceptions and typed rule options. Explanation describes the reason shown for this rule’s decision. Offer common HTTP methods through selection, plus explicit access to supported custom/imported methods; never drop an unlisted method or narrow protocol capabilities.

Label **Default policy: Allow / Deny** and explain it applies only when no rule matches; either default permits both rule effects. Show actual priority and tie behavior. Reorder controls have a keyboard equivalent, explain unavailable directions and preserve effective ordering; never auto-change numeric priorities. Rule removal changes only the draft until apply and says so.

Open policy testing as a focused dialog retaining all UX-IN04 inputs/results. State no downstream request or credential substitution occurs. Closing returns to the originating section, item and safe scroll/focus context without marking the service dirty. Do not stack dialogs: finish/cancel a rule dialog before opening another task. Validation is local plus linked summary; all supported advanced controls remain reachable without a long expanded main page.


## UX-IN17 — Service review comparison and approval

Approved by UX-DESIGN-005. Applies only to service review, preserving existing global Settings/SMTP behavior and all authorization, audit and atomic publication boundaries.

### Comparison

New settings is the first and default tab; Changes is the second tab. In Changes, show only changed fields, grouped using existing configuration sections: Details, Allowed servers, Authentication, Request rules, Secret detection, and Additional configuration when needed. Each aligned pair names its field or existing item and shows Before/After. Green + Added, red − Removed, amber ~ Changed have visible text and symbols; use light tints behind dark readable values. Preserve equal column widths, shared row alignment and exact sanitized values. Do not clip, truncate or normalize literals. Empty strings, false, zero, null, empty collections and absent properties remain distinguishable. Added items have Before “Not configured”; removed items have After “Removed”. An absence marker is not a literal value.

Treat list identity and order accurately: matching stable identities may compare field changes; added and removed identities remain distinct even when shown alongside each other. The synthetic rule replacement illustrates one removal plus one addition, not a rename or fabricated identity match. Position/order changes are explicit; never sort arrays to hide differences. Preserve exact regex, custom methods, options, nested typed values and own-property-safe identifiers. Display advanced values in named rows and bounded readable substructure, not a whole-object dump or nested accordion tree. A no-baseline service says “No active configuration yet” and proposed content is additions; no changes says “No configuration changes” and still permits viewing New settings. Do not invent a no-op Apply when existing lifecycle has a separate enable/review action; preserve that action’s actual consequences.

New settings presents the complete sanitized proposal in named section cards, using two columns at wide sizes and one column when space is insufficient. Common values use domain labels. Additional supported values remain available with exact types and ordering. Metadata about credential availability is distinct from configuration values; raw credentials never appear. Immediate credential/access changes are not presented as pending draft changes. Existing review data sanitization applies before either tab is rendered.

Both tabs refer to the same immutable reviewed scope, base and dependencies; switching is read-only and never saves, applies, resets input, dirties the draft or changes the confirmation target. Keep service identity, reviewed revision, effect summary and return-to-edit action visible. No filtering removes required review information. Keep tab selection in local view state, not credential-bearing persistent storage.

### Confirmation and outcomes

Show each actual reviewed security exception as a visible bullet at the end, with the same safe scope-specific meaning used in its acknowledgment. Replace the generic administrator/secret-detection disclaimer here; do not hard-code three exceptions. With none, state that no security exceptions exist. These bullets do not acknowledge anything and do not remove the separately required modal checkboxes or truthful protection limitations elsewhere. Place Approve changes in the existing bottom action bar. It opens a focused modal; it performs no mutation. Copy: “This will apply changes and make this the active configuration.” Name the service and current reviewed revision. With no security exceptions, Continue is enabled after the existing valid review prerequisites, and Cancel is available. With exceptions, add “Before changes can be applied, please review and acknowledge the following:” and one unchecked checkbox for each required exception. No acknowledge-all shortcut. Continue stays disabled until every required checkbox is selected. Show the remaining count for multiple exceptions. Checkbox labels describe the risk and readable affected scope; acknowledgments bind the exact reviewed state and are not stored across reopened/stale reviews.

Cancel or Escape before submission closes the modal without mutation, preserves review/tab/scroll and returns focus to Approve changes. Continue sends only the exact reviewed scope through existing authorization, dependency, audit and atomic activation controls. Pending submission disables duplicate Continue and announces Applying; it must not offer a cancellation that claims to undo an admitted request. Known success names the new active revision; known rejection explains why and preserves safe work. A changed dependency, permission or revision invalidates acknowledgments and requires renewed review. Unknown outcome shows status verification, never a guessed rollback or blind retry. Existing readiness blockers remain actionable before approval and cannot be acknowledged away.

### TLS exception language

TLS verification has a service default and destination overrides. Never claim it is always per-service or always per-destination. For inherited off: “Server certificate verification is off — https://api.example.org inherits the service default. The server’s identity will not be verified.” For an explicit destination override, say “Overridden for [safe destination label]”; list only the actually affected destinations. An on override is not included in an off list. Explain the default separately if relevant; avoid “all servers” unless it is true of the reviewed effective scope. A destination permitting both HTTP and HTTPS describes TLS as applying to HTTPS requests and HTTP as a separate cleartext exception.

Use safe familiar configured labels when meaningful, otherwise sanitized host/base address and, if necessary, an ordinal to disambiguate. Do not expose URL userinfo/query secrets or rely on internal primary/secondary identifiers as the only label. Do not fabricate a destination display-name capability. Retain existing exception classification and acknowledgment identities; improve presentation without weakening or silently merging required acknowledgments.
