## D13-01 — Complete filtered exports with bounded work

Current evidence export uses offset plus500 and a2MiB whole-response limit. That is explicitly superseded for Activity by PO-FB327. A successful Activity file contains every authorized retained match in its admitted snapshot, independent of page/size. Preserve the established100,000 retained-row and2-second aggregate selection budget, including predicate evaluation, and exact authorization/filter semantics. Exceeding that budget is an explicit failed operation, never zero matches, a partial successful file or a silently broader/narrower query.

Serialization/delivery must remain bounded and cancellable, with bounded buffering and bounded concurrent work. Do not retain the old2MiB ceiling as a normal completeness cap or silently split/truncate a claimed complete file. A bounded incremental delivery mechanism may support the complete selected result without an unbounded in-memory JSON copy; a persistent export job, new storage product or retention hold is not required. Preserve the existing evidence schema/UTC instants and sanitized nested criteria. A failed or interrupted output is not represented as a complete download. Every new transport path must retain authenticated admission, CSRF where required, current role/session/service scope, audit admission/outcome, no raw query/credential logs, and negative authorization tests. If asynchronous work is used, recheck authority before releasing output, invalidate stale navigation/UI completions, and terminate/clean up bounded work on cancellation. Other exports retain their existing bounds.

Search resolves relative ranges at deliberate Search/Refresh (initial default entry once), yielding absolute inclusive UTC instants. Paging/page-size changes reuse those criteria; they do not recompute the interval. Each response describes its current retained snapshot, not a promised immutable database snapshot. Filter edits immediately invalidate displayed rows/count/page/export state. Export requires the current successful searched criteria but evaluates a fresh authorized snapshot, so retention/new events may change the count. No polling, durable search snapshot, or new Member export privilege.

## D13-02 — Archive verification without Activity installation

PO-FB337/350 supersedes archive-to-Activity materialization for every accepted archive version, including legacy valid archives. Both archive audit domains and nested archived importedAudit are excluded from the newly installed live/queryable Activity sources. Removing only UI labels, hiding rows, skipping only one source, or disabling only new-format exports is insufficient. Backups may retain archived audit evidence; the archive's integrity, chain/head identity and dependency verification remain mandatory even for content that will not be installed. Separate validation from materialization; do not bypass verification because Activity is excluded. Existing size/time/worker/job limits, protected staging, leases, exclusive publication, clean-host proof and recovery-material gates remain.

Preserve the current host's independent journal and gateway audit, including events after the snapshot and restore/enrollment/resume operations. Already installed current-host imported domains are retained under existing retention and confidentiality rules: do not purge or replace them from archive contents, and do not reimport duplicates. A clean host starts its own local Activity with installation/recovery events, without claiming archived continuity. Retain non-queryable verification/provenance metadata needed for recovery validity and security attribution, but never expose incoming archive rows indirectly through query/detail/export. This exclusion concerns the archive being installed, not previously installed current-host imported domains, which retain their existing authorized query/export/retention behavior. This does not remove snapshot account/credential historical metadata or weaken fresh incarnation, disabled service, enrollment, revoked-session and rollback safeguards. A failed installation restores the coherent prior local state; crash recovery must not accidentally replay the archive materialization path. No general-purpose evidence upload is introduced.

## D13-03 — Settings semantic equality and safe complete review

Opening forms or converting equivalent units for presentation creates no mutation. Domain equality may compare validated semantic scalar units/defaults, while preserving meaningful case, exact identifiers, regex, order and typed options. Never deserialize/rewrite source literals merely to make review look clean. Browser dirty state and durable saved proposals are separate; real stored drafts remain in the full authorized review even when their panel was not visited. An untouched retention edit cannot synthesize a protection draft. A genuine stale protection proposal still needs repair: automatic refresh is permitted only with proof of the same target/proposal existence, generation, exact content and relevant baseline; freshly inspect current dependencies. A changed proposal, dependency, authority or uncertain write cannot be rebased by blind retry.

Review/apply remains one prepared atomic configuration transaction with exact actor/session/revision/dependency binding, full-scope acknowledgment and specific risks (including unencrypted SMTP). Moving acknowledgments to a modal does not weaken server enforcement, recent authentication or immutable reviewed scope. Cancel changes nothing. Confirmed Apply returns to its originating section; unknown results are persistent until durable lookup, never automatically repeated or announced as success. Retention cleanup remains separately reported post-commit work. Service immediate values/current Access, staged SMTP Set/Replace and independent confirmed Clear remain intentional exceptions.

## Assessment

Good: current exact predicate scopes, audited admission, recovery cryptographic validation, independent current-host audit and atomic Settings preparation are appropriate and retained. Risky: retaining old500-row semantics would contradict complete export; removing archive verification with import materialization would cross the recovery trust boundary; blind stale-draft retry could overwrite actual work. Change only these bounded contracts and their directly affected presentation/state transitions. Do not redesign authorization, storage, cryptography, audit retention, backup format, full recovery lifecycle or introduce a general job/notification center. Bounded positive/negative delivery qualification is required; no production security issue is asserted from this definition-only assessment.
