# Information architecture

## UX-IA01 — Shell, navigation and orientation

Use four primary areas in this order: **Services**, **People & Access**, **Activity**, **Settings**. Services is the landing page. Show instance name as context, never as an implied tenant switcher. Show current area, selected service and page title. Highlight the active global destination and selected service/Settings section with visible accent plus weight or shape, and expose current-page/selected-tab state programmatically. A persistent **My account** control exposes password, MFA/recovery codes, own browser sessions and logout. Own connected clients are accessible from both My account and People & Access. Preserve account/logout reachability on narrow screens even though the compact prototype omits this control.

Only show destinations the actor may use. Owner receives all areas. Administrator receives service configuration/access, eligible-identity assignment, activity and non-secret People list/detail and bounded account editing under SECRES-06; Owner-only instance settings are readable where non-secret configuration is authorized but not editable; shared secret-detection editing remains available under the PRD scanning permission. Auditor receives read-only configuration and evidence, including read-only Settings, and no MCP execution or mutation affordances. Member sees assigned-service discovery and connection information, own activity, My account and My connected clients; hide global people administration and instance settings. An empty assigned-service list explains how to contact an existing administrator without adding a request-access workflow. Unauthorized direct navigation shows a permission-safe explanation and return path without disclosing restricted object details.

## UX-IA02 — Services and object context

Use a searchable service list with status filtering including Archived. Show name/description, runtime lifecycle (Draft, Active, Disabled, Archived), separate unapplied-change state, access summary and configuration attention. Do not imply that an Active service's draft is live. A security exception stays visible on the relevant row/detail. Owners/Administrators get **Add service** and **Import configuration**; Members get connection guidance for eligible assigned services; Auditors inspect non-secret details.

Service detail uses **Overview**, **Configuration**, **Access**, **Activity** tabs. Overview summarizes effective destinations, authentication availability, policy, security exceptions and lifecycle. Configuration edits the draft, with applied revision/history accessible. Access shows current explicit assignments; changes are immediate confirmed actions. Activity opens the shared activity view scoped to this service. Preserve search/filter and return context when returning to Services.

Initial Add service follows the PRD's five steps: Details → Destination → Authentication → Access & policy → Review. Show progress, preserve non-secret entries on Back, and support saving incomplete drafts. An incomplete service cannot activate. Review names proposed grants and required credential availability; they are not historical grants that can later be replayed. Existing services use the grouped editor rather than forcing the setup wizard on every edit.

## UX-IA03 — Configuration coverage and disclosure

Keep ordinary fields visible and advanced capabilities one named, focused action away; do not nest multiple fold-outs in service configuration. A settings search matches field labels/help and opens the containing section; it searches non-secret labels, never credential values. Guided forms and advanced editor operate on the same draft without lossy conversions. Existing regex rules remain regexes unless the user deliberately replaces them. No service-specific templates or profile packs are introduced.

| Location | Required capability placement |
| --- | --- |
| Service Configuration → Details | Name, description, documentation link with its LLM-use explanation; stable MCP service reference remains discoverable/copyable and read-only after creation |
| Destinations | Multiple server cards with base URL and explained host matching; always-visible service-default certificate verification; focused per-destination advanced settings for schemes, ports, matching, exact reference and inherit/on/off verification override |
| Authentication | Multiple credential identities with availability/version/last-successful-change actor and time; explicit No downstream authentication choice; placement/name/prefix/suffix/header-ownership controls; separate write-only value creation/replacement/deletion |
| Request policy | Default allow/deny, ordered rules, explicit numeric priority, methods, host/path matching, reasons; exact/prefix/regex path choices; safe policy tester |
| Secret detection | Effective Secretlint and sensitive-name settings, catalogs, extend/replace modes, rule options, custom patterns/exclusions and allow patterns; per-rule exceptions; binary controls |
| Configuration tools | Same-draft advanced editor, sanitized export, import validation and revision history; historic configuration opens as a fresh permitted draft |
| Settings → Secret detection | Shared scanning defaults/catalogs and effective inheritance; roles follow the PRD configuration/scanning permissions, not an Owner-only navigation assumption |
| Settings → MCP authentication | Built-in OAuth clients/scopes/principal/token lifetimes; advanced external OAuth registrations and legacy bearer; distinct console security context; Owner writes only |
| Settings → Limits | Existing request/response byte limits, timeouts, concurrent work, references, denial records, authentication and scanner capacity; values with units, current consumption and capacity outcome; Owner writes only |
| Settings → Email | Optional SMTP, sender, encryption/credentials, test and delivery status; manual-link fallback; Owner writes only |
| Settings → Backups & restore | Encrypted backups, schedule/retention, job history/progress, download, restore preview and recovery; Owner only |
| Settings → Health & retention | Gateway/storage/audit/scanner/SMTP/backup health, audit retention and operational guidance; view/write authorization follows the PRD |

No duplicated competing settings: shared defaults belong in Settings and effective inherited summaries appear inside each service. Links take eligible actors to the defining setting. A read-only inherited value states its source. Exact technical field names remain available in advanced help/import errors to correlate with existing configuration.

## UX-IA04 — People, clients and evidence

People & Access exposes the fixed role label and a concise permission explanation; do not imply Owner/Administrator automatically executes services. Owner manages invitations, disable/reactivation, restored-user review and permitted roles. Owner and Administrator manage permitted email/contact and role changes under SECRES-06. Owner and Administrator get separate **Reset password** and **Reset Authenticator** controls for permitted other-user targets under SECRES-05. Administrator may target another Administrator, Auditor or Member, never an Owner, with non-secret detail visibility under SECRES-06. Owner may target other eligible human users including Owners. Self-service stays in My account. Disabled/deleted users, unaccepted invitations, unreviewed restored users and external/legacy identities are excluded. An otherwise eligible MFA-restricted target may receive an authorized replacement factor-reset proof. Administrator may edit another non-Owner contact and change roles among Administrator, Auditor and Member, but cannot edit an Owner, grant Owner, change their own role, invite, disable/reactivate, perform restore review or administer others’ sessions/grants. Permitted self-contact editing follows SECRES-06. Administrator can still select existing eligible identities for service assignments. Clearly separate pending invitations, active users, disabled users and pending recovery. Keep disable/revoke reachable from person/client detail without navigating through configuration drafts.

My connected clients lists the user's grants and revocation action. ChatGPT and Codex connection instructions are distinct. Display copyable non-secret origin and complete MCP URL separately (for example https://mcp.example.org and https://mcp.example.org/mcp), network reachability guidance and authorization context. OAuth consent identifies client, requested scope and acting identity; it never implies that consent itself grants a service assignment. Auditors receive no execution connection action.

Activity provides time, actor, service, action, result and request-ID filters, readable event rows and sanitized details. Service Activity reuses these controls. Show request outcome, policy reason and admitted revision, including uncertain recorded outcomes. Explicitly distinguish local events from imported archive provenance and unavailable intervals. Export honors the visible authorized filter scope; Members have only own permitted reads, not global export. Saved request bodies, raw secrets and opaque references are never detail views.

Import is available from Services and Configuration tools. Offer clearly named inputs for the legacy gateway YAML and both optional scanner catalogs; preserve missing-file defaults and supported identifiers, ordering, literal regexes and exceptions. Import opens a role-permitted draft and never silently activates services or reads arbitrary host files/environment variables. Show validation issues by field/source location, unknown fields, unresolved credentials and identity mappings. Permit correction in a draft; no silent dropping or inferred email-based grant. Import/existing environment precedence is explained at handover. History shows sanitized changes, actor and revision; **Use as draft** states that old access, lifecycle and credential values are not restored.


## UX-IA05 — Focused Settings navigation

Use six Settings destinations, in this order: Secret detection, MCP authentication, Limits, Email, Backups & restore, Health & retention. Initial Settings entry opens Secret detection; direct links/back preserve the destination. Show the selected global area and selected Settings destination using accent, weight/shape and programmatic current-page semantics. These are navigation links, not ARIA tabs pretending to be separate pages. Narrow layout uses an ordinary labeled select with the same choices and current selection. Existing global navigation and account/logout remain reachable.

Each destination renders only its own content. For authorized editors, start directly with populated non-secret fields from current state or clearly labeled saved pending changes; no redundant summary-then-Edit step. Read-only actors see readable values with the same grouping. Do not show all groups in a long accordion. Secret detection may have named internal disclosures for its two catalogs and advanced options. Backups, restore and health keep task-specific job/status views alongside populated forms for editable schedule, retention and diagnostics. Member has no Settings destination; Administrator can edit secret detection and inspect other authorized non-secret settings; Auditor gets equivalent readable summaries without edit controls. Backups and backup-recovery administration remain Owner-only; assisted account resets follow SECRES-05.

All editable instance sections operate on the existing settings draft. Editing another section neither applies nor discards it. A persistent change summary names changed sections and distinguishes In use, Saved for later · Not in use yet, and Unsaved changes. Section navigation or a search jump with unsaved edits offers Stay, Save for later and continue, or Discard unsaved edits and continue. Discard here affects only unsaved current-section input; it does not delete another section's saved draft. Save for later never applies. Review changes validates and durably saves authorized pending work before opening full-scope review; it never activates settings. Full-page Review all changes lists every changed section before applying the exact reviewed set atomically. No per-section partial apply is introduced. Returning to edit restores the selected section and safe values. A stale base/dependency/role requires a sanitized comparison/reload and re-review, retaining only currently authorized non-secret work. Immediate value/security actions remain distinct and can stale the draft.

Settings search matches authorized labels, help and optional technical aliases, never secrets. Results show section and field label; choosing one follows the same unsaved-edit guard, selects the section, opens the named disclosure and focuses the field or read-only value. Do not reveal unauthorized destinations or secret values. Empty search explains no matching settings; clearing search restores the selected section. An error summary can navigate to a failing field in another section, preserving safe work. Session expiry, offline uncertainty, permission loss and durable-audit failure follow existing UX-IN05; no hidden auto-save, silent replay or secret browser persistence.


## UX-IA06 — Friendly control and summary coverage

All preserved supported fields need a labeled control in forms, including advanced disclosures. Raw JSON/YAML is optional expert tooling, never the only route for an existing capability. General-purpose existing rule-option objects use a bounded typed key/value/list editor with add/remove rows; they are not replaced by a JSON textarea. Values whose nature is technical (regex, claim name, URL, scope) remain literal labeled inputs with explanatory help. Preserve imported literal values and matching semantics; do not infer conversions from regex to a simpler matcher. Unknown imported fields produce explicit validation errors.

| Capability | Friendly editing | Read/effective summary |
| --- | --- | --- |
| Service identifier, name, description, docs | Labeled text/URL fields; stable ID read-only after creation | Name, purpose, stable ID and documentation link |
| Multiple destinations, base URLs, schemes, ports | Repeatable destination cards; URL, scheme and numeric port inputs; explicit exact/suffix/regex matcher choice | Allowed destination labels and matching mode; broad/cleartext exceptions |
| Service/destination TLS | Verify toggle and destination Use service default/override choice | Effective verification and source; exception visible |
| Multiple credential identities, no-auth | Credential cards and explicit No downstream authentication choice; write-only value actions distinct from metadata | Availability/version/last change; no value reveal |
| Placement/name/prefix/suffix/header ownership | Placement select; named literal inputs; gateway-owned-header toggle with effect help | Human-readable placement/template with placeholder, not real secret |
| Service access | Eligible-identity list and explicit assignment actions | Current assignments; never historical implicit grants |
| Policy defaults and ordered rules | Allow/deny selector; repeated rule cards with ID, numeric priority, methods, host matcher, exact/prefix/regex path and reason | Actual effective evaluation order, matching types, default and exceptions |
| Rule scanning exceptions and binary controls | Rule-detail toggles, disabled-rule checklist, size value/unit or supported unlimited option | Effective scanning, disabled rules, binary guard and bypass consequence |
| Secretlint catalog and rule options | Existing/default rule list with status; Extend/Replace selector; add/edit rule and typed option controls; custom pattern/exclusion rows | Catalog mode, effective rule list, overridden entries and active exceptions |
| Sensitive-name catalog | Separate Extend/Replace selector; named pattern rows and allow-pattern rows | Effective patterns and exemptions; matching semantics explained |
| Shared versus service response protection | Inheritance choice and explicitly labeled override editor; links to shared source | Effective settings and defining scope; no competing duplicated defaults |
| Built-in MCP OAuth | Allowed-client URL rows, scope rows, duration number/unit fields and principal settings as supported | Mode, origin versus MCP URL, allowed clients/scopes, lifetimes; console auth remains distinct |
| External OAuth and legacy bearer | Named advanced mode selection; issuer/audience/JWKS/claim/scopes fields; exact registered identity controls in existing identity surface; write-only bearer handling | External issuer/subject registration and shared-attribution warning; no implied console login |
| Login throttling | Numeric attempt/capacity fields and time units grouped under MCP authentication | Effective windows, thresholds and lockout limits |
| Request/response sizes and timeouts | Number plus units; separate inbound/outbound/response and read timeout labels | Effective value/default and capacity outcome |
| Concurrency, references, denial records, maintenance, scanner capacity | Named numeric/duration controls grouped by request work, saved references/denials, authentication work, scanner work; per-source/subject/service distinctions preserved | Effective limits, available current utilization and exhaustion behavior; do not fabricate unavailable metrics |
| Email | Enabled state, host/port, encryption select, sender and authentication identity fields; write-only creation/replacement through draft/apply; independent confirmed deletion; applied-state test | Configured/not configured, safe sender/server labels, credential availability and latest delivery/test outcome; manual fallback |
| Backups and retention | Schedule and retention fields; existing Create/download/restore actions and dedicated review | Encrypted archive/job status, recovery point, retention and off-host responsibility |
| Health, audit retention, diagnostics | Health cards; retention value/unit; existing supported diagnostic level choice | Component status and actionable failure; audit authority and host-only storage/key configuration remain host-side |
| Import, export and history | Import configuration entry from Services and Configuration tools; explicit main YAML and optional catalog uploads, field-linked validation and resolution steps | Import summary, unresolved credentials/identity mappings, sanitized diff and applied revision; no implicit activation |

Forms, optional advanced editor, import preview and read summaries use the same permitted draft without dropping fields. Show supported opaque rule-option structure through typed controls and readable nested labels; unsupported forms must preserve the value and flag a specific implementation gap, never silently flatten it. The form contract does not add configuration knobs for host-only key material, filesystem paths or startup essentials.


## UX-IA07 — Account list and detail

People & Access uses one row per human account: account link, role, lifecycle status and Last console sign-in. The link or row opens a full account detail page; retain a real keyboard-accessible link and preserve return/filter context. No inline edit cards in the list, modal stacks or new bulk administration. Detail groups editable email/contact and role, read-only user ID/Created/Last console sign-in, recovery actions and permitted access actions. Owner and Administrator controls follow SECRES-06; visibility never grants mutation authority. Do not invent extra profile fields.

Creation and last sign-in show timezone and STATE-07 meanings. Never, Unknown and Not applicable are distinct. Restored last-sign-in metadata identifies the backup source until a new qualifying local sign-in replaces it. Creation, metadata, enrollment and lifecycle are not editable form values. Own password/MFA remain in My account.

## UX-IA08 — Plain terminology and current-value discovery

Use **Secret detection** for the former Response protection destination and service group. Explain immediately: “Checks data returned by services for credentials before sending it to your MCP client.” Keep best-effort limitations and destination trust readable; do not imply universal prevention. Search accepts the old term and exact technical aliases. Other ordinary labels/actions use concrete verbs and explain unavoidable technical terms. Copy across navigation, hints, review, validation, errors and outcomes must agree. All UX-IA06 capabilities remain accessible, including exact patterns/options and advanced fields.

Settings shows loaded current values or explicitly pending values, never literal undefined or made-up sample defaults. Loading, unavailable, unconfigured and unreadable state are distinct. Health/jobs remain status views; editable diagnostics/retention use current-value forms. Do not duplicate a stale “applied diagnostics” summary beside a newer editor.


## UX-IA09 — Focused service configuration and lifecycle navigation

Service rows show name/description, lifecycle, separate pending changes and configuration attention. A real service link supports keyboard navigation and a full-row pointer hit area excluding sibling actions. Place permitted Enable/Disable and Delete on the right; unavailable activation has a nearby explanation and corrective route, never an apparently usable activation for an incomplete imported service. Active is a lifecycle state, not proof of reachability or executable readiness. Active plus Draft changes is represented simultaneously; Active plus Value missing explains blocked execution independently.

Service Delete uses the existing archive lifecycle: confirmation explains removal from normal use, immediate blocking of new requests, retention of configuration/history/audit and the ability to restore as Disabled. Retain Archived filtering and explicit review before re-enabling. No permanent purge is introduced.

Keep Overview, Configuration, Access and Activity. Overview summarizes the configuration actually in use using connection, authentication availability, policy and access/exception groups; do not flatten raw object structure. No applied configuration says “No configuration is in use. This service cannot run yet.” A pending-draft notice provides a specific review route. Current exceptions remain visible.

Configuration opens directly in populated role-permitted non-secret fields, grouped into Details, Destinations, Authentication, Access & policy, Secret detection and Review changes. Render one section at a time. Show one editing-state context rather than redundant draft/unchanged banners. For read-only roles retain identical grouping as readable values. A single service-wide Guided/Advanced switch changes the complete draft representation; do not repeat Advanced Editor links in individual sections. Existing services use directly navigable sections; creation retains its five linked steps. Review follows the same groups. Never discard literals or unsupported advanced values on mode/section transition.

Technical references are not deleted or renamed for presentation. Preserve imported service, destination, credential and rule identifiers exactly. Service ID is MCP-visible and remains discoverable/copyable with an explanation. System-only destination/rule identifiers may move to focused advanced settings; explicit technical editing remains reachable. No automatic identifier migration is implied.

## UX-IA10 — Explicit access and imported identity recovery

Access explains who may use this service through an MCP client, that an administrative role alone grants no execution, and that request rules still apply. Existing-service assignments have permitted immediate confirmed add/remove controls; initial activation identifies proposed assignments awaiting review. Read-only actors get labeled values without mutation controls. Do not confuse assignment selection with resolving an imported identity reference.

An unresolved import identifies each original subject, its exact non-secret source location and affected services, and provides a direct mapping route inside the saved draft. An eligible account selector requires explicit selection; no email/name inference. Saving a mapping preserves unrelated draft edits and does not itself grant execution. Show remaining issues and a path to review; re-upload is not the only recovery. If an identity needs registration, explain the appropriate permitted registration route. Stale/ineligible selections require correction without silently granting access or losing safe work.

Shared Secret detection defaults remain in Settings. Service pages show their source and effective value; a separate link explicitly names the Settings destination and wider impact. Guard unsaved service work before leaving. No unexpected global-settings jump within the ordinary policy-rule task.
