# Operating evidence

Activity combines retained management operations and gateway events. Filter exact actor, service, action, result or request ID and UTC time bounds. Service Activity opens the same view with its service filter. Details identify local provenance, admitted revision and uncertain starts without a recorded completion. An uncertain outcome is not proof that downstream work failed: inspect before repeating an action.

Owners, Administrators and Auditors inspect authorized instance evidence and export activity, access inventory, configuration/security exceptions, or software/job status. Members read only their own acting identity; being the target of another user's management action does not grant its event. Members have no global export. All export APIs recheck current permission and require durable audit admission and completion. Audit outage and restricted diagnostic sessions preserve scoped reads but block export.

Pagination permits 1–100 events, with offset at most100000. Activity export selects at most500 rows from one snapshot and indicates truncation; narrow the filter or select the next offset for another audited export. Reports are at most2MiB. Work scans at most100000 combined projected events with a2second work budget. Each durable raw/chain file has a64MiB safety ceiling; journal admissions have a100000record ceiling. Exhaustion fails closed rather than silently evicting evidence or shortening retention. These are engineering safety bounds, not user/service tiers. Plan disk capacity and reviewed retention before exhaustion; host repair is required after a failed durable append.

Only allowlisted metadata appears in reports. Credential values, reusable/opaque tokens, headers/cookies, enrollment proofs, seeds and request/response bodies are excluded. Caller labels/reasons have controls removed and exact known credential/pattern redaction; URL queries/fragments and user information are removed. Sanitization and response scanning remain best-effort protections, not universal non-exfiltration guarantees.

Settings → Audit retention defaults to365days. Only an Owner can save a draft, review its deletion count/cutoff, and apply that exact review. Another committed state change requires fresh review. An hourly bounded sweep uses the same durable admission gate; no web interface edits individual events. Shorter retention deletes expired complete evidence and appends an attributed receipt with cutoff/count/previous chain head. Unresolved operation starts and unexpired OAuth revocation intents remain even when older than retention. Receipts themselves remain protected evidence.

Compaction verifies disk integrity first and writes a signed, fsynced redo record before replacing raw evidence, chain and checkpoint. Restart completes only an authenticated pending transaction; invalid or missing integrity material fails closed. An interrupted completion remains uncertain until host repair/restart and inspection. More than one local sink sharing a writer prevents compaction until only the normal application sink remains. Keep the complete audit directory, integrity keys and checkpoints together; no individual-file repair or unaudited truncation is supported.

Local keyed integrity cannot protect against a hostile host administrator or host loss. Operators must keep independently protected external evidence copies and establish access review, patching, incident response and storage monitoring. These reports do not establish SOC2 certification. [Encrypted backup](console-backups.md) health reports actual archive availability, recovery/completion/outcome, conditional daily target and retention failure. Restore installation and reenrollment remain M17.

Settings → Limits and capacity groups all 39 effective request, HTTP, reference, retained-state, scan and worker controls. Seconds preserve exact millisecond values; MiB preserve exact bytes. Enter whole milliseconds, bytes or counts. Each field names consumption and capacity behavior; request-local sizes/deadlines have no accumulating usage counter. OAuth login thresholds/lifetimes remain in MCP authentication, binary scan bounds in each service policy, and scanner finding/time bounds share Response protection. Those existing editors and email delivery remain reachable in Settings. Fixed transport/storage and console-session safety boundaries appear separately.

Only an Owner can save, review and apply instance limits. Review is bound to actor, current configuration and identity state. Lowering capacity preserves occupied counters, grant/code state, references, denials, pending metadata requests, active scanner jobs and queued jobs. New allocation blocks until usage is below the new bound; expiration continues normally. Idle surplus scanner workers retire once their admitted jobs finish. Existing work keeps its admitted deadline and protection context. Lowering name coverage/findings capacity is an explicit scanning exception, not a protection guarantee. Timestamp-based reference and denial lifetimes support long safe-integer durations; actual Node timers are bounded separately.

Health reports safe gateway/storage/audit/scanner/email states and capacity recovery guidance. Missing, replaced or permissive stable application keys, missing audit keys/checkpoints/files and failed durable storage block sensitive work. Public `/health` exposes only bounded ready/not-ready status. Email configuration alone does not prove delivery: use an admitted test and inspect actual delivery results. Backup reports actual job outcomes, verified current archive availability, missed conditional daily targets, storage/catalog capacity and separate retention failures. Historical completion alone is not current recoverability. Repair from the host, preserve complete directories, then restart and inspect uncertain operations; an existing restricted diagnostic session never upgrades.

Forwarded headers grant no trust in this release. Configure the application origin explicitly, terminate remote HTTPS at an operator-controlled proxy, strip incoming forwarded headers and keep administration private. The socket peer is authoritative for source admission; deployments must account for shared proxy-source capacity rather than assume caller-supplied addresses are trustworthy.
