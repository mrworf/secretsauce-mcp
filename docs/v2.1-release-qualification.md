# SecretSauce v2.1 exact-candidate qualification

Use this runbook on one disposable Docker amd64 qualification host and one
representative HTTPS deployment. It records the evidence M10 cannot infer from
unit tests or a prior release. A missing or failed step remains release
blocking.

Never paste an enrollment code, password, TOTP seed/code, cookie, CSRF or
step-up proof, OAuth value, API key, credential, opaque reference, raw request
or response body, full client address, or private hostname into the record.

## Recorded local candidate evidence

Executable candidate `bfac16c` passed the automated build, 169-file/1,097-test
suite, OpenAPI parity, and 14-artifact readiness validator on 2026-07-30.
Its authorized production audit reports zero findings through Moderate.
`better-sqlite3` 13.0.2 installs without the deprecated `prebuild-install`
path and passed bundled-binary, forced source-build, persistence, and
rootless-container qualification.
Rootless Docker Engine 29.6.1 on linux/amd64 with VFS storage passed container
build and release smoke. The candidate image ID was
`sha256:b2ef16bc5d640a9523f6807f52cac205a07a4f5107daf151c323aa9119dd68a6`.

The preceding candidate's clean topology reached enrollment and completed the
enrollment, ordinary-login, current-session, logout, post-logout rejection,
and unauthenticated-MCP contracts without recording secret values or response
bodies. Application recreation preserved operational readiness, emitted no
replacement initial-enrollment value, and left both containers healthy. The
vault had network mode `none`, no published ports, a `0700` runtime-owned store,
and the declared read-only inventory mounts.

Both envelope-root rotations also completed against disposable snapshots of
that preceding candidate.
Identity rotation alone received a writable database inventory; vault rotation
kept that inventory read-only. Exact-request replay and journal resume were
exercised. A populated vault record survived vault-root rewrap, retained
runtime ownership and mode, and remained decryptable after normal topology
recreation.

This is prior automated and HTTP-contract Compose evidence, not current
exact-candidate Compose qualification or a visual or
assistive-technology browser qualification. An in-app browser was unavailable.
An authenticated live MCP tools journey, the complete database/OAuth/audit and
ephemeral-authority matrix, hosted clients, and independent/human approvals
remain release-blocking. Browser end-to-end testing is explicitly scheduled
after M10; the automated browser and accessibility contracts remain part of
this candidate's M10 evidence.

The database-authority topology cannot substitute the qualification bearer
mode for that journey: an exact-candidate probe correctly rejected the bearer
subject because it was not an active durable user. Completing the gate requires
an approved externally reachable HTTPS client-metadata document and the real
built-in OAuth flow (normally supplied with the hosted-client deployment).

## Candidate record

Record:

- exact Git commit and clean-tree result;
- image digest and build time;
- Docker Engine and Compose versions, OS/architecture, rootless/rootful mode,
  storage driver, and filesystem;
- public MCP/OAuth origin and separate control origin using redacted
  `example.org` stand-ins in portable artifacts;
- reviewer names/roles, client versions, UTC timestamps, and sanitized request
  status or correlation identifiers only.

The executable commit changes if a remediation touches source, configuration,
container definitions, generated contracts, or dependencies. Rerun every
affected gate against the new commit.

Run from a clean checkout:

```text
npm ci

npm run build
npm test
npm run check:control-openapi
node scripts/validate-v2.1-readiness.mjs

```

The advisory command sends dependency metadata to the public npm registry.
Run it only under the organization's approved disclosure/network policy. No
High or Critical production advisory may remain.

## Clean official Compose journey

Use a dedicated Compose project and empty volumes. Confirm the target is
disposable before removing volumes; never apply the cleanup command to an
existing installation.

```text
docker compose -p secretsauce-v21-qualification -f docker-compose.example.yaml config
docker compose -p secretsauce-v21-qualification -f docker-compose.example.yaml up --build --detach
```

Before enrollment:

1. Confirm the vault container has network mode `none`, exposes no port, and
   owns only its declared generated/setup/runtime/store and read-only inventory
   mounts.
2. Confirm the application exposes bounded setup liveness/status and the setup
   page, while ordinary control, OAuth, MCP, authentication, database, and
   credential behavior is unavailable with the documented bounded response.
3. Confirm the application did not open SQLite before the vault reported
   validated readiness and that setup polling remains bounded during a forced
   vault restart.
4. View the current application log interactively, use the labeled enrollment
   value without copying it into a transcript, and complete browser enrollment.
   Confirm restart invalidates unused process-lifetime authority and successful
   enrollment never emits another initial value.
5. Confirm the final enrollment transaction creates one active superadmin,
   password and TOTP together; returns to ordinary login; and does not
   automatically create a browser session.

Through the browser, create and publish a minimal no-credential service with an
`https://api.example.org` destination, assign one ordinary user, and activate
database runtime authority using the documented interactive transition while
the ordinary application writer is stopped. Do not add a service-specific
profile or real downstream hostname to portable evidence.

After activation, verify:

- control and gateway readiness are sanitized and ready;
- login, logout, current-session revocation, all-session revocation, and agent
  grant revocation take effect on the first newly authenticated request;
- MCP initialize, tools/list, `list_services`, and one policy explanation work
  without `mcp-session-id`;
- the browser, logs, audit, SQLite projections, and captured sanitized
  responses contain no prohibited values.

## Recreation and durable state

Record volume identities and safe row/count summaries, then force-recreate both
containers without deleting volumes. Confirm:

- generated keys, setup manifest, database, vault store, OAuth grant state, and
  audit history survive;
- bootstrap authority, browser process memory, OAuth codes, vault boot
  capabilities, and `gref_`/`sec_` references do not survive;
- existing eligible browser/OAuth state follows its documented stable-key and
  durable-record behavior;
- new runtime references work and old references fail safely;
- audit appends after recreation and no second SQLite writer is admitted.

Do not use `docker compose down --volumes` until every required result is
recorded and the project name and host are confirmed disposable.

## Root rotations and degraded dependencies

Using consistent disposable snapshots, execute both `identity` and `vault`
envelope-root rotations from the [operator guide](operator-guide.md). Cover
pre-switch interruption, post-switch resume without repeated arguments,
exact-request replay, cross-target request reuse rejection, retained-key loss,
storage failure, and application setup-only gating during maintenance. Confirm
only the identity rotation temporarily makes the database inventory writable
to the vault.

Exercise vault unavailable/retrying/fatal states, audit write failure, database
lock/schema failure, source-trust rejection, capacity rejection, OAuth client
metadata timeout/size/DNS rejection, and concurrent revocation. Every public
result must remain bounded and sanitized.

## Hosted Codex and ChatGPT

Follow the [client compatibility checklist](client-compatibility.md) for both
hosted clients. The OAuth resource and issuer are the origin
`https://mcp.example.org`; the client MCP Server URL is
`https://mcp.example.org/mcp`. Record setup gating, login, restart, refresh,
cross-subject reference rejection, grant revocation, and bounded temporary
unavailability. A platform-side action block is separate from a gateway result
and does not prove the gateway journey passed.

## Human and independent reviews

Named reviewers must cover:

- security/invariants and the final role/scope/route table;
- architecture, persistence, single-writer operations, and rollback/recovery;
- UX/accessibility at 320 px, wide layout, 200% zoom, keyboard-only use,
  visible focus, live status, paste/autofill, reduced motion, dark mode, and a
  representative screen reader;
- data/API schemas, OpenAPI parity, pagination, errors, idempotency, and
  immediate invalidation;
- deployment, source trust, Compose storage/isolation, backup/restore,
  rotation, troubleshooting, and documentation links/commands.

Each review records findings, severity, disposition, residual risk, and an
explicit approve/block decision. Agent-authored analysis may prepare evidence
but is not labeled independent or human.

## Closure

Update [the release matrix](release-matrix.md) only from recorded
exact-candidate evidence. M10 is complete only when every row is `pass`, every
acceptance criterion is checked, all blocking remediation is closed on the
final candidate, and the acceptance artifact states exact versions, fixtures,
results, residual risks, and approvals. No gate is waived.
